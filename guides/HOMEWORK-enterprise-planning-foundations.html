Homework — learn Enterprise Planning as a consultant

Draft Homework 7 assignments Updated 2026-09-06 Answer key

Goal: explain an LN planning result from demand through execution, identify the effective configuration that caused it, predict the result of one controlled change, and prove the explanation with Item Order Plan and Order Pegging.

This is a six-sitting curriculum for the planning processes documented in this library. Complete it in order. Do not continue when a result is unexplained: capture it, restore the baseline if safe, and report what remains unknown.

Warning

Change only the bamboo test items in Company 4100. Record the baseline before every change and restore it afterward. Every capture must show the whole LN window and readable status bar.

2. Sitting 2 — trace demand before generating anything Not started

Use BAM-CHOP-PAIR. In Item Order Plan, identify every demand and supply row before running planning.

What is current on-hand inventory?

Inventory on Hand on the form header, before any grid row is applied. The Overview grid's running balance starts from it

Which rows are sales demand?

Rows whose Order Type is Sales Order, each carrying its demand quantity and the sales order number it comes from

Is there a safety-stock requirement?

Only if Safety Stock is set on the item's ordering record. A safety-stock top-up appears as a demand of its own, and planning answers it with supply of its own, separate from the sales-order-driven supply

Is any demand carrying a Specification indicator?

Not settled in this library. The help says a specification check box is present on a demand line when demand pegging applies, and says nothing about what it shows. Open one demand row, capture the line with the box visible and the status bar readable, and hand the capture in with your report-back; it goes to the library's inbox and this sitting is updated from it. Not documented for this release.

Which rows are actual supply and which are planned supply?

Actual supply is an existing order with a number and a status — a purchase order advice, a production order. Planned supply is what the run created — a Planned Production Order or planned purchase order, status Planned — and it exists only until it is transferred

What is Planned Available after each row?

Planned Available is a running balance: the previous row's figure, minus that row's demand, plus its supply, starting from Inventory on Hand

Can you reconcile the running balance as prior balance − demand + supply?

Yes, and it reproduces every value on screen. It is the one arithmetic the grid makes visible; pegging is what explains which demand a supply answers

Open Order Pegging for each planned supply. Record the exact demand it answers. Treat the grid quantity as the result and the pegging tree as the explanation.

4. Sitting 4 — horizons, time fences, and run scope Not started

Read Items - Planning before opening the planning run.

Order Horizon

Read it on the item's Items - Planning record: the workdays you enter, and the date LN shows for them. A deployed value belongs to this environment on this date and is not printed here; write down what you see and when

A demand dated after the current date plus the horizon's workdays. Planning does not see it, so no planned order answers it, and nothing says why

Planning Horizon

Read it on the same record. If Master Plan is cleared the field is not editable and its date equals the order horizon's

The total period an item is planned for. It is editable only with Master Plan selected; without a master plan it equals the order horizon, so for these items it adds no boundary of its own

Time Fence

Read Time Fence and its unit, and whether Use Time Fence is selected — a fence that is not in use is no boundary

The date a set number of workdays ahead. Inside it, what a run does to existing planned orders depends on Use Time Fence together with Generate within on the generate session — check both before reading a result as a fence effect

Forecast Time Fence

Read it on the same record; it is counted on the enterprise unit's calendar, falling back to the company's

Before it, planning counts only actual customer orders; beyond it, demand is actual orders plus forecast. A forecast-driven planned order can only appear beyond the fence

Then open Generate Order Planning (Item) cprrp1220m000, which has no menu entry and is reached from the item-planning context. Record the state of Include Parent Items, Include Child Items, Generate within, Confirm within, Update Pegging Relations, and Automatic Order Grouping.

Run two controlled tests:

  1. Generate from a component only and record whether parent demand is included.
  2. Generate from the top-level item with Include Child Items selected and record which components are planned.

Captures to hand in:

The item's Items - Planning record with all four horizons and Use Time Fence visible

Generate Order Planning (Item) as run, with every check box and range visible

Planned Orders after each of the two controlled tests

At 10 days, every requirement whose date falls inside the window that opens at the first requirement is netted into one planned order — the library saw three requirements become one on 2026-09-05. 6. Sitting 6 — transfer, execution, and exception handling Not started

Review the result in Planned Orders, select one planned order, and follow the documented transfer path.

What planned-order type was generated?

Read Order Type on the row in Planned Orders: a planned production order for an item whose supply source is production, a planned purchase order for one whose supply source is purchase. The item's ordering data decides which

Which demand does it answer?

Open the planned order and its pegging. The pegged demand names the sales order line, or the safety-stock requirement, that this supply exists for; the grid quantity is the result and the pegging is the explanation

What transfer session opens?

Transfer Order Planning cppat1210m000, opened from the rows selected in Planned Orders

Does Combine Orders apply to this order class?

Only to the four classes that have a Combine Orders field at transfer — subcontracting, intra-company distribution, purchase and multicompany distribution. An ordinary job-shop planned production order has no equivalent, so for production supply the answer is no

What real order number was created?

Process Report on Transfer Order Planning lists the orders processed with the numbers they became, and Error Report lists what did not transfer and why. If nothing transferred and no error printed, the orders were still Planned and the Transfer Status … as Well box was not ticked — that is a status, not an error

Where does the order appear in execution?

A planned purchase order becomes a purchase order, one order for several planned ones where Combine Orders was selected. For production supply the transfer has not been walked in this environment: capture the resulting production order, or the exact error, with the status bar readable and hand it in; this sitting is updated from it. Not documented for this release.

Which report, warning, or exception message was produced?

Read both reports on the transfer. One message is already known for a purchased item with no buy-from business partner: the transfer fails and says the purchase order cannot be generated because the buy-from partner cannot be determined. Any other message is worth a capture: it goes to the library's inbox and the session file gains it

For purchase supply, compare generation-time Order Interval with transfer-time Combine Orders in Transfer Order Planning cppat1210m000, reached from selected rows in Planned Orders. Explain why they can both reduce the number of visible orders while acting at different stages.

For production supply, treat the transfer as a test: it has not been walked end to end in this environment. Capture the transfer report or exact error and the resulting production order. Not documented for this release.

Not documented for this release.
